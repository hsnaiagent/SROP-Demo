# Version 1 UI Documentation

## Overview

This app is a single-page SROP validation and planning demo. It has three main panes:

1. **Submissions**
2. **Flags**
3. **SROP Plan**

All state is stored in `app/page.tsx`, and the panes are pure presentation components. The app loads by fetching `/api/validate` in the background, then reveals results when the user clicks **Run Validation**.

The UI is designed to support these scenarios:
- page load / validation prefetch
- run validation
- inspect and triage flags
- email query drafts and simulated responses
- justify issues with notes
- gate plan generation until all flags are resolved
- render a before/after plan comparison

---

## Page layout

The page has a vertical layout with three sections:

- header
- `SubmissionsPane`
- `FlagsPane` (revealed after validation)
- `PlanPane` (revealed after validation)

### Header

The header includes:
- title: `SROP Validation & Planning`
- summary text from the validation result

The summary text is populated from the `summary` returned by `/api/validate`.

## 1. Submissions Pane

Component: `app/components/SubmissionsPane.tsx`

This pane represents the four incoming stakeholder files.

### Visible elements

- section title: `Submissions`
- action button
  - label changes by phase:
    - `Run Validation` when waiting to validate
    - `Validating…` while the UI is in the validating state
    - `Validated` after the result is revealed
  - the button is disabled if:
    - submission metadata is not yet loaded
    - phase is `validating`
    - phase is `triage` or `planned`
- error banner
  - shown when a validation request fails
  - red border and text
- grid of four submission cards

### Submission card contents

Each card shows:
- source name
- status dot / badge
- file name
- arrival time text
- row count
- column headers preview

#### Status dot variants

`StatusDot` displays:
- spinner while `phase === 'validating'`
- a red badge with the count of flags when validation is complete and the source has flags
- a green check mark when validation is complete and the source is clean
- a neutral gray dot before validation completes

### Additional behavior

- The four cards are always shown, even during load; placeholders show `loading…` until metadata arrives.
- `ARRIVAL_TIMES` are static fake offsets from `app/demo-data.ts`.
- `meta.submissions` is loaded by `loadSubmissionMeta()` in `app/api/validate/route.ts`.

### Scenarios

- **Initial page load**
  - cards show placeholder text until backend metadata returns.
  - action button is `Run Validation`.
- **Validation in progress**
  - button changes to `Validating…`
  - a spinner is shown in each status dot.
- **Validation complete**
  - button becomes `Validated`
  - sources with flags show a red badge with a count.
  - clean sources show a green check.

## 2. Flags Pane

Component: `app/components/FlagsPane.tsx`

This pane appears once validation has been revealed. It groups flags by `source` and also shows clean sources.

### Visible elements

- section title: `Flags`
- open count summary: `{openCount} of {flags.length} flags open`
- source sections
  - each source with one or more flags gets its own group
  - each clean source gets its own clean summary box

### Flag card contents

Each flag card contains:
- severity badge
  - high = red styling
  - medium = amber styling
  - low = zinc gray styling
- rule label
  - derived from the rule constant, e.g. `historical deviation`
- file name
- row reference
  - rendered from `rowRef`, e.g. `JAZAN · BP-JAZAN · DIESEL · 2026-10`
- evidence text
  - shown in monospace and larger text
  - this is the key credibility line with both numbers
- plain English summary
  - italic text quoting the flag description
- action controls depending on status

### Flag statuses and transitions

The app models these statuses in `lib/types.ts`:
- `open`
- `awaiting_response`
- `responded`
- `justified`
- `corrected`

The user can transition each flag through these flows.

#### Open state

When a flag is `open`, the card shows two buttons:
- `Accept as justified`
- `Send query email`

##### Accept as justified
- opens a reason panel
- requires a non-empty note
- on confirm, the flag becomes `justified`
- the UI shows `Justified — “{note}”`

##### Send query email
- opens an email editor panel
- the draft is copied from `serverEmails` if Node 2 returned it,
  otherwise it is generated by `buildEmailDraft(flag)`
- fields:
  - `To`
  - `Subject`
  - `Body`
- buttons:
  - `Send`
  - `Cancel`
- on send, the flag becomes `awaiting_response`

#### Awaiting response state

When a flag is `awaiting_response`, the email panel remains visible and shows:
- destination email address text
- subject text
- status label: `awaiting response…`
- button: `Simulate response`

Clicking `Simulate response` transitions the flag to `responded` and populates a simulated reply from `CORRECTIONS`.

#### Responded state

When `responded`, the card shows:
- quoted response text
- a button to accept the response
- button label is either:
  - `Accept correction ({value})`
  - `Accept response`
- on accept, the flag becomes `corrected`
- `correctedValue` may be set for the one numeric correction scenario

#### Justified state

When `justified`, the card shows:
- `Justified — “{note}”`

#### Corrected state

When `corrected`, the card shows:
- `Corrected — {submittedValue} → {correctedValue}` if a numeric correction exists
- otherwise `Resolved — confirmed, no data change`

### Clean source cards

For every source listed in `cleanSources`, the pane renders:
- source header
- a green-bordered box with `No issues found — clean submission.`

### Scenarios

- **all flags open**
  - user must either justify or send queries before plan generation unlocks
- **some flags in progress**
  - `awaiting_response` and `responded` are still open for gating
- **flag justification**
  - user enters a required note and confirms
- **query email path**
  - user opens email, edits draft if desired, sends it
- **simulated stakeholder response**
  - user clicks `Simulate response`
  - response text is shown
  - user accepts it
- **corrected outcome**
  - if the response includes `correctedValue`, the resolved value is displayed
  - if it is only a confirmation, the card shows a resolved state

## 3. SROP Plan Pane

Component: `app/components/PlanPane.tsx`

This pane shows the gate and, once generated, the plan comparison.

### Visible elements

- section title: `SROP Plan`
- generate button
  - label:
    - `Generate SROP Plan`
    - `Regenerate SROP Plan` if a plan already exists
    - `Generating…` while generation is in progress
  - lock icon shown when gate is closed
  - button style changes depending on `gateOpen`
  - shake animation runs when generation is refused while gate is closed
- status text shown when gate is closed:
  - `Resolve all {totalFlags} flags to generate — {openCount} still open`

### plan summary card

When a plan exists, the pane shows:
- label: `Total revenue`
- submitted revenue
- validated revenue
- delta revenue in color:
  - red if negative
  - green if positive

### plan comparison table

The table has columns:
- `Month`
- `Refinery`
- `Product`
- `Submitted`
- `Validated`
- `Δ`

It renders two row types:
- excluded rows
- regular plan rows

#### Excluded rows

These appear first. They show:
- refinery
- product with bulk plant in parentheses
- text `excluded — no reference limits`
- this explicitly preserves excluded series such as LPG-95

#### Plan rows

Each row compares:
- submitted production
- validated production
- delta production

Rows with changes are highlighted with a light amber background.

### Scenarios

- **gate closed**
  - generate button is disabled
  - user sees open flag count
- **gate opens**
  - all flags must be resolved by status transitions
  - `gateOpen` becomes true only when no flags remain in `open`, `awaiting_response`, or `responded`
- **plan generation success**
  - `plan` is loaded and displayed
- **regenerate**
  - if a plan already exists, the button label changes to `Regenerate SROP Plan`

## UI states and transitions

The app tracks `phase` in `page.tsx` as:
- `idle`
- `validating`
- `triage`
- `planned`

### Idle

- page has loaded
- `/api/validate` is already fetching in the background
- submissions are visible in placeholder form
- run validation button is enabled

### Validating

- button text becomes `Validating…`
- status dots spin
- no additional panes are shown yet

### Triage

- validation result is revealed
- `FlagsPane` and `PlanPane` are now visible
- open count and clean sources update
- plan generation remains gated until all flags are resolved

### Planned

- a plan has been generated and is displayed
- the generate button can still be used to re-run the plan

## Data flow and integration points

### `/api/validate`

- sends a POST request from the browser when validation is revealed
- calls `validate()` in `lib/north.ts`
- returns:
  - `flags`
  - `cleanSources`
  - `summary`
  - `emails` (optional)
  - metadata about submissions
- includes error handling and returns a hint to enable `MOCK_MODE`

### `/api/generate`

- is purely local and stateless
- loads the CSV-based plan input from server-side `lib/csv.ts`
- calls `buildPlan()` twice:
  - once on submitted data
  - once after applying corrections
- returns:
  - `raw` plan rows
  - `resolved` plan rows
  - `excluded` row keys
  - revenue metrics

## All example scenarios

### Scenario 1: clean run
- page loads
- background validation prefetch begins
- user clicks `Run Validation`
- validation completes
- sources without flags show green check marks
- flags are displayed grouped by source
- user resolves each flag by justifying or accepting a response
- gate opens
- user clicks `Generate SROP Plan`
- plan comparison appears

### Scenario 2: error during validation
- user clicks `Run Validation`
- `/api/validate` returns an error
- error banner appears in `SubmissionsPane`
- button remains available for retry after the error is cleared

### Scenario 3: accept a flag as justified
- user clicks `Accept as justified`
- reason textarea opens
- user enters a required note
- user clicks `Confirm`
- status becomes `Justified`
- the flag no longer counts as open for the gate

### Scenario 4: send a query email
- user clicks `Send query email`
- email editor opens with `To`, `Subject`, `Body`
- user edits if needed
- user clicks `Send`
- flag status becomes `Awaiting response`
- the panel updates to show the sent email details
- user clicks `Simulate response`
- flag status becomes `Responded`
- user accepts the response
- if a numeric correction exists, it is shown as corrected

### Scenario 5: gate refusal
- user clicks `Generate SROP Plan` while flags remain open
- button animates `shake`
- message explains how many flags remain
- no plan is generated

### Scenario 6: plan generation
- with the gate open, user clicks `Generate SROP Plan`
- `/api/generate` returns plan results
- revenue summary and table appear
- changed rows are highlighted
- excluded series are explicitly displayed

## UI element summary

### `app/page.tsx`
- owns all React state
- prefetches validation result on mount
- handles transitions for flag actions, email/reason flows, simulation, and plan generation
- passes props to the three pane components

### `SubmissionsPane`
- shows file metadata and source arrival timing
- renders the action button and error banner
- communicates validation progress with status badges

### `FlagsPane`
- renders flags grouped by source
- displays evidence and plain language text
- manages triage actions across five statuses
- shows clean submission summaries

### `PlanPane`
- renders the gate button
- shows the plan summary box
- renders the before/after comparison table
- preserves excluded rows for unmatched series

---

## Notes

- The UI deliberately does not perform real email sending.
- `Simulate response` is a demo-only shortcut used to move the y-axis of the flow from query to resolution.
- The full plan table includes both submitted and validated production values and shows the delta as the business impact.
- The gate is UI-only; the backend does not enforce it.
- The app is intended for a staged demo where validation is already available when the user clicks `Run Validation`.
